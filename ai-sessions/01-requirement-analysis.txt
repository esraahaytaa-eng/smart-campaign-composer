⏺ I've read CASE.md. Here's my analysis. As you asked, there's no architecture
  and no technology choices yet; Vue and Go are already fixed by the case.

  1. What the system has to do, in one line

  The AI suggests, the backend checks, the marketer approves, the system sends.
  Claude only proposes things. Everything it produces has to be checked by the
  backend, approved by a person, and then executed by code we control.

  2. End-to-end user flow

  #: 1
  Step: Write request
  Actor: Marketer
  What happens: Writes a request in plain language ("30% discount… Istanbul…
  cart, no purchase…")
  What can go wrong: Request is vague, off-topic, or tries to inject
  instructions
  ────────────────────────────────────────
  #: 2
  Step: Create audience
  Actor: Claude → Backend
  What happens: Claude returns audience rules as JSON. The backend checks them
  against an allowlist of fields and operators, turns them into a safe query,
  and shows the match count split by SMS and email permission
  What can go wrong: Invalid or unknown fields, 0 matches, ambiguous meaning
  ────────────────────────────────────────
  #: 3
  Step: Generate content
  Actor: Claude → UI
  What happens: SMS text, email subject and email body stream to the screen.
  When
  the stream ends, the backend validates lengths and variables
  What can go wrong: Over the length limits, invalid JSON, stream cut off
  ────────────────────────────────────────
  #: 4
  Step: Review and edit
  Actor: Marketer
  What happens: Previews messages with real-looking variable values, edits them,

  and the server re-checks the edits
  What can go wrong: Edits break the limits or use unknown variables
  ────────────────────────────────────────
  #: 5
  Step: Approve
  Actor: Marketer
  What happens: The campaign is locked and the audience and content are frozen
  What can go wrong: Double approval, edits after approval
  ────────────────────────────────────────
  #: 6
  Step: Send
  Actor: Queue → Workers → Mock providers
  What happens: Up to 100 messages/s per channel, permission checked per
  channel,
  no duplicates, retries on failure
  What can go wrong: 429s, temporary errors, worker crash, duplicate sends
  ────────────────────────────────────────
  #: 7
  Step: Track
  Actor: Dashboard
  What happens: Live counts of queued, sent, failed and retrying messages, plus
  metrics and health endpoints
  What can go wrong: Stale numbers, numbers that don't add up

  3. Functional requirements (mandatory)

  - Audience: rules are structured JSON and checked against an allowlist. Never
    run SQL that came from the AI. Show the match count. Check SMS and email
    permissions separately and never break them.
  - Content: SMS ≤ 160 characters and email subject ≤ 80. Support variables like
    {{first_name}}. Stream the content, allow preview and editing, and re-check
    every edit on the server.
  - Sending: an async queue, a limit of 100 messages/s per channel across all
    workers, no duplicates, retries, and mock providers.
  - Mock providers: they must simulate success, delays, temporary errors and
    HTTP 429.
  - Monitoring: a live dashboard, metrics endpoints and health endpoints.
  - AI: structured JSON output that is validated, invalid output handled safely,
    a mock LLM so tests run without an API key, and the key read from
    ANTHROPIC_API_KEY with a .env.example.
  - Data: 5,000 fictional users with name, email, phone, city, cart and order
    history (with timestamps), and separate SMS and email permissions. They're
    created on a fresh docker compose up, and running it again creates no
    duplicates.

  4. Non-functional requirements

  - Security: the AI never produces SQL. The API key stays in env vars only.
    Recommendation: send Claude only the rule schema and the request, never user
    records, so no personal data goes to the LLM. Edited content must be safe
    to show in the preview, so it can't run as HTML or script there.
  - Reliability: the queue guarantees at-least-once delivery, and an idempotency
    key turns that into "no duplicate sends". A crashed worker must not cause
    messages to be lost or sent twice.
  - Simplicity and maintainability: the case says this directly. Pick the fewest
    moving parts.
  - Operability: one-command setup, make test without an API key, and health and
    metrics endpoints.
  - Performance: the scale is small. 5,000 users at 100/s is about 50 seconds
    per channel, so this is about correctness, not throughput.

  6. Gaps, unclear rules and edge cases

  1. Channels: does every campaign send both SMS and email, or does the marketer
     choose?
  2. SMS length with Turkish characters (important): characters like ş, ğ, ı and
     İ push SMS out of the GSM-7 character set. In the UCS-2 encoding that
     replaces it, one SMS segment holds only 70 characters. The case also
     doesn't say whether the 160 is counted before or after {{first_name}} is
     filled in.
  3. What counts as a duplicate: the same user, campaign and channel only, or
     also across campaigns (a frequency cap)? Two users could also share the
     same phone number.
  4. When the audience is fixed: at approval or at send time? Should permission
     be checked again just before sending, in case a user opts out in between?
  5. Editing audience rules: can the marketer edit the rules directly, or only
     re-prompt Claude?
  6. Login and roles: none are mentioned. Is there one marketer and no login?
  7. Retry policy: how many attempts, what backoff, which errors are retryable
     (429, 5xx, timeout) vs permanent, whether to honour Retry-After, and what
     the final failed state is.
  8. Campaign lifecycle: can a campaign be cancelled or paused while it's
     sending? Can an approved campaign be edited?
  9. Variables: which ones are allowed, and what's the fallback if a user has no
     first name? Unknown variables should be rejected.
  10. Email body: plain text or HTML, and is there a length limit?
  11. Business meaning: does "did not buy anything" mean in the last 30 days or
      ever? Claude will interpret this, so the marketer should see the rules it
      chose in readable form.
  12. Status detail: is "accepted by provider" enough, or do we also simulate a
      separate "delivered" step?
  13. Edge cases: an audience of 0, a request that has nothing to do with
      marketing, Claude timing out or rate-limiting us, the stream dropping
      halfway, and approving twice.

  7. Technical risks

  - Keeping the 100/s limit global for each channel when several workers run at
    once.
  - Retries combined with crashes leading to duplicate sends.
  - Streaming output vs JSON validation: streamed JSON is incomplete until the
    end, so it can only be validated once the stream finishes.
  - Claude giving different output each time, which makes tests
    non-deterministic. The mock LLM solves this.
  - Startup order in compose (database ready, then seed data, then app) and
    making sure seeding is idempotent.
  - The process risk of scrubbing ai-sessions/ for keys and personal data.

  8. Main system responsibilities (not components yet)

  Managing campaigns and their status, AI orchestration (prompting, parsing,
  validating, falling back), audience rules into a safe query, permission
  enforcement, content validation and filling in variables, the approval
  workflow, dispatching (queue, rate limit, duplicate prevention, retries), mock
  providers, status tracking with live updates, observability, seeding data,
  and config and secrets.

⏺ Your approach works and it's the easiest to explain: validate at send time, 
  skip with a reason, report it. I'd keep that as the core. Before we lock it
  in, here's my review.

  What I like
  - One rule, applied in one place: the worker. No fallback text, no extra
    content for Claude to generate, no second approval.
  - Nothing is ever cut short or changed silently. Whatever is sent is exactly
    what the marketer approved.
  - It scales naturally, because each message is checked on its own as it goes
    out.

  Risks
  1. "Resend to skipped" isn't actually simpler. It's a second feature. It needs
     a new kind of audience, "recipients of campaign X skipped on channel Y for
     reason Z", alongside the rule-based audience. It also needs a link between
     the parent and child campaigns, a second approval, and duplicate
     prevention that covers both campaigns. That's more work than the fallback
     field we just dropped.
  2. The marketer finds out late. Skips only show up after sending starts. For a
     time-sensitive discount, skipped users get it later or not at all.
  3. Channels are skipped independently. A user can be skipped on SMS and still
     get the email. Any resend has to target only the channel that was skipped.
  4. A resend still has to follow every rule. Permissions are checked again (the
     user might have opted out since), and the new content can also be skipped
     again. That's fine, but it has to be tested.

  Simpler alternatives
  - A warning before approval, without blocking. The single count query from
    before still costs almost nothing: "about N recipients may be skipped due to
    character limit". It's information only, with no rendering and nothing
    loaded into memory. It lets the marketer shorten the text before sending,
    which often makes a resend unnecessary.
  - Do the resend later. The core would be validation at send time, skipping
    with character_limit_exceeded, and skip counts and reasons on the dashboard.
    "Resend to skipped" would come after the main flow works, like the other
    optional features. Duplicate prevention by user, campaign and channel
    already guarantees nobody gets the same message twice.

⏺ You're right. A unique constraint stops us from creating two message records,
  but it can't stop us from sending the same record twice. The dangerous moment
  is when the provider has accepted the message but our status update never
  happens: a crash, or a timeout where the outcome is unknown. The standard fix
  is at-least-once processing combined with an idempotent receiver. Here's what
  I recommend:

  1. One message record = one idempotency key
  - Each (campaign, user, channel) gets exactly one message record, protected by
    a unique constraint.
  - That record's ID is the idempotency key. It's created once and reused on
    every attempt, so it stays the same across retries, crashes and restarts.

  2. The provider deduplicates by key
  - The worker sends an Idempotency-Key header with every request.
  - The mock provider remembers the keys it has seen. A repeated key returns the
    original result and is not sent again, and the response is marked as a
    replay so we can see it in metrics.
  - This is the contract our mock enforces. It also matches how real providers
    that support idempotency work.

  3. Message states and crash recovery
  pending → sending (lease until T) → sent
                                    → retry_scheduled (next_attempt_at) → 
  sending …
                                    → failed            (permanent / attempts 
  exhausted)
                                    → skipped           
  (character_limit_exceeded, no consent)
  - When a worker picks up a message, it claims it with a lease, a short time
    window during which only that worker may process it.
  - If the worker crashes, the lease expires and the message gets picked up
    again. The same key goes to the provider, the provider replays the original
    result, and we mark the message sent. The effect is that each message is
    delivered exactly once.

  4. Retry policy (proposed defaults)

  ┌───────────────────────┬─────────────────────────────────────────────────┐
  │        Outcome        │                     Action                      │
  ├───────────────────────┼─────────────────────────────────────────────────┤
  │ 429                   │ Retry, honouring Retry-After if present         │
  ├───────────────────────┼─────────────────────────────────────────────────┤
  │ 5xx, timeout, network │ Retry with exponential backoff plus jitter      │
  │  error                │ (≈1s, 2s, 4s, 8s…, capped at ~30s)              │
  ├───────────────────────┼─────────────────────────────────────────────────┤
  │ Other 4xx (e.g.       │ failed, no retry                                │
  │ invalid number)       │                                                 │
  ├───────────────────────┼─────────────────────────────────────────────────┤
  │ Character limit / no  │ skipped, no retry                               │
  │ consent               │                                                 │
  ├───────────────────────┼─────────────────────────────────────────────────┤
  │ Max 5 attempts        │ Then failed with the last error recorded        │
  └───────────────────────┴─────────────────────────────────────────────────┘

  Retries count toward the 100/s per-channel limit, so a wave of retries can't
  push us over it.

  One caveat to record: if the mock provider keeps its keys only in memory,
  restarting the provider loses that dedup history. For a mock that's acceptable
  as long as we document it. A real provider keeps idempotency keys for a fixed
  period.

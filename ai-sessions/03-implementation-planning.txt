⏺ Here's the proposed schema: 13 tables in three groups, plus one table for the
  mock provider.

  categories ─┐
              ├─< order_items >── orders >── users ──< cart_items >── categories
              │                               │
              │                               └──< messages >── campaigns ──< 
  campaign_content
              │                                       │            │
              │                                       └──< delivery_attempts
              │                                                    └── marketers
  ──< sessions
  provider.idempotency_keys   (separate schema; linked only by message ID as the
  key)

  Customers and shopping
  - users: profile, city, language, sms_opt_in, email_opt_in, and signed_up_at
    (enables "new customer" campaigns).
  - orders(user_id, ordered_at, total_amount) and order_items(order_id, 
    category, quantity, unit_price). An order can span several categories, so
    category lives on the item.
  - cart_items(user_id, category, quantity, unit_price, added_at).
  - categories: a lookup table with about 6 rows. It keeps category values
    consistent, and the AI prompt and rule validation can read the list from it.
  - I left out a products table. Nothing in the rules or message variables needs
    product names, and a category on each item is enough. It can be added later
    without changing the other tables.

  Campaigns
  - campaigns: holds the request, the chosen channels, the rules as validated
    JSON, status, version, and who created, approved or cancelled the campaign,
    with timestamps.
  - campaign_content(campaign_id, channel, subject, body): one row per chosen
    channel, so there are no empty email columns on an SMS-only campaign (D1).
    If A/B testing or per-language messages are added later, a variant or
    language column fits into the key.

  Delivery tracking
  - messages: the current state of each (campaign, user, channel). It doubles as
    the queue (D18), with lease and retry fields.
  - delivery_attempts: one row per provider call, recording the outcome
    (accepted, rate_limited, server_error, timeout, network_error, rejected) and
    the HTTP status. It provides the retry and 429 counts the dashboard needs
    (D16), an audit trail for debugging, and attempt timestamps for the
    rate-limit test. Cost: one extra insert per attempt, at most 200/s.

  Campaign scenarios the rules can express (each one is a parameterized
  subquery):
  - Cart abandonment: cart activity within N days and no order since.
  - Win-back: last order more than N days ago.
  - VIP: total spend or order count at least X.
  - Category affinity: ordered or carted a given category within N days.
  - High-value cart: cart value at least X.
  - New customers: signed up within N days.
  - City.

  Scheduled sending is still deferred as an optional feature. It would fit later
  with one nullable campaigns.scheduled_at column, a scheduled status and one
  extra condition in the claim query, so I haven't added it now.

  Trade-offs to weigh:
  - Without a products table you can't target specific products.
  - delivery_attempts grows by one row per attempt, which is fine at demo scale.
  - These new rule types extend the D14 catalog, so they need your approval and
    a DECISIONS.md entry.

⏺ I've updated the plan with your four points. One of them, the seed date
  refresh, is a new proposal from me and needs your OK.

  1. Scheduling from the brief
  - The request is sent with the browser's time zone, and Claude also gets the
    current time. Claude returns a suggested send time and the phrase it read,
    for example "yarın saat 10:00".
  - A badly formatted time counts as invalid output and triggers the one retry
    from D15.
  - A time in the past or more than 30 days ahead isn't filled in. A note
    explains why, and the audience rules are still used.
  - Vague timing such as "next week" gives no suggestion, just a note.
  - The suggestion is only a proposal on the draft. On the review screen it
    appears as "Suggested from your brief: Tue 22 Oct, 10:00 (Europe/Istanbul)",
    with Schedule preselected and the time editable.
  - Approval requires an explicit choice of Send now or a specific time, so a
    suggested time is never used without the marketer confirming it.

  2. Language
  - Both the mock and the real AI reply in the language of the request,
    including Turkish.
  - The mock is now a small keyword reader that recognizes cities, day counts,
    cart/sepet, order/sipariş, categories, spend amounts and simple time
    phrases. That way the demo without an API key handles varied briefs.
    Anything beyond that is left to real mode.

  3. Seed data and relative dates (needs your OK)
  - Problem: dates fixed at the first docker compose up slowly drift out of
    windows like "last 30 days", so the demo looks empty weeks later.
  - Proposal: every migrate run, which happens on each up, shifts all order,
    cart and signup dates forward by the time since the last run. The data
    always looks as if it was seeded today.
  - It adds or removes no rows. Approved campaigns aren't affected because their
    audience is fixed at approval. It never runs while the app is running.
  - Users are generated from fixed profiles with set shares: cart abandoner,
    recent buyer, lapsed buyer, VIP, new signup, browsing-only and inactive.
    Every 7/30/60/90-day window, category and city therefore has a predictable,
    non-empty audience. Tests pin both the shift and the coverage.
  - The alternative is to reseed with docker compose down -v. It's simpler, but
    it wipes all campaigns, and the demo still looks empty if started weeks
    later.

     │ Scheduled sending flow (in scope, approved 2026-10-21; audience frozen  │

     │                                                                         │
     │ 0. Suggestion from the brief: the request is sent together with the     │
     │    browser's IANA time zone. Claude gets the current time and that      │
     │    zone, and returns suggested_send_at (RFC 3339 with offset) or null,  │
     │    plus schedule_note (the phrase it read, e.g. "yarın saat 10:00").    │
     │    Vague timing ("sometime next week") → null with a note. The backend  │
     │    validates it: a bad format is invalid output and triggers the D15    │
     │    retry. A parseable time outside the window (in the past, or more     │
     │    than 30 days ahead) isn't prefilled; the note explains why           │
     │    ("'yesterday 10:00' is in the past") and the rules are still used. A │
     │    valid suggestion is stored as the draft's proposed send_at. It's     │
     │    advisory only; nothing is scheduled yet.                             │
     │ 1. Review and confirm: the review screen shows "Suggested from your     │
     │    brief: Tue 22 Oct, 10:00 (Europe/Istanbul)", with Schedule           │
     │    preselected and the time editable, or Send now. Approve always sends │
     │    an explicit send_at (or now) from what's on screen, so a suggestion  │
     │    is never accepted implicitly. A draft changed since it was viewed    │
     │    fails the version check (D10).                                       │
     │ 2. Approve: the marketer chooses Send now or Schedule (date and time in │
     │    browser local time with the zone shown, stored in UTC). In one       │
     │    transaction (T9): check version, status draft, valid content,        │
     │    audience > 0, and send_at: now → now(); scheduled → at least now + 1 │
     │    min and at most now + 30 days. Rules are evaluated once, and         │
     │    messages are inserted with next_attempt_at = send_at. The campaign   │
     │    gets status = approved and send_at.                                  │
     │ 3. Waiting: no new status and no scheduler process. The UI shows        │
     │    "Scheduled for <time>" while status = approved AND send_at > now().  │
     │    The worker's normal claim (next_attempt_at <= now()) doesn't pick    │
     │    these messages until the time comes. Content and audience can't be   │
     │    changed. Cancel works as D11 already defines (approved → cancelled,  │
     │    pending messages → cancelled). Rescheduling isn't supported: cancel  │
     │    and create a new campaign.                                           │
     │ 4. Sending: at send_at the messages become due. The first claim flips   │
     │    the campaign to sending, and from there the normal path runs:        │
     │    consent and campaign-status re-check, rendering, length check, rate  │
     │    limiter, retries (D7, D8, D19). It ends as completed when every      │
     │    message is final.                                                    │
     │ 5. Late start: if the worker is down at send_at, sending starts when it │
     │    comes back. The dashboard shows the scheduled time and the actual    │
     │    first attempt (earliest delivery_attempts.started_at).               │
     │ - Known trade-off (accepted via D8): users who match after approval are │
     │   missed, and a buyer who purchases after approval still gets the       │
     │   reminder. Only consent is re-checked.                                 │

⏺ Here's my assessment. I haven't changed the plan.

  1. Recalculating the audience when sending starts

  I think this is the right call now that scheduling is in scope. A marketer who
  writes "people who added to cart in the last 30 days but didn't buy" means as
  of the moment the message goes out. With the audience fixed at approval,
  someone who buys in between still gets the "you didn't buy" reminder.

  How it would work
  - At approval: rules, content and send time are fixed. The screen shows the
    current count per channel and says it may change: "412 recipients now (SMS 
    380 · Email 301). The audience is recalculated when sending starts on 22 
    Oct, 10:00; the final number may differ." No message records are created
    yet.
  - When sending starts: the worker finds approved campaigns that are due. In
    one transaction it evaluates the rules, creates the messages (the unique
    constraint still prevents duplicates) and sets the campaign to sending.
    "Send now" takes the same path about a second later, so there's only one
    code path.
  - During sending: nothing changes. Consent is still re-checked per message.
  - Dashboard: shows "Estimated 412 at approval → 398 at send".
  - Side benefit: cancelling before the send time gets simpler, because no
    messages exist yet.
  - Cost: D8 is replaced by a new decision. The approved count becomes an
    estimate, and a user who matches and then stops matching while a send is
    running is not removed.

  Briefs with a cutoff date or a fixed audience. This is where your proposal
  exposes a gap. Today every time rule is relative ("within N days").
  - Cutoff dates: "added to cart since 1 October" or "bought during Black
    Friday" would be stored as "within 20 days", and if the send starts 5 days
    later the window silently moves. Fix: time rules accept either a relative
    form (in the last 30 days, counted from send time) or an absolute form
    (since 1 Oct 2026 or between 24 and 28 Nov). Claude uses the absolute form
    when the brief names a date, and the rule chips show which form it is. This
    is a small extension of the rule catalog and its validation.
  - "Exactly these users, as they are now": with absolute dates and consent
    re-checks, the only difference from a snapshot is that newly matching users
    get added. That's usually what a marketer wants. A per-campaign "freeze
    audience at approval" option would reuse the same function, just called
    earlier, so it's cheap to add later. I wouldn't build it now: it's a second
    mode to explain and test, and no current brief needs it.

  2. Over-limit counts and a shorter alternative template

  This works well with a dynamic audience, because the decision is made per
  recipient at send time anyway (D3). The count at approval is an estimate over
  the current audience.

  - On the approval screen, per channel: "SMS: 37 of 380 would exceed 160 
    characters" and "Email: 2 of 301 subjects would exceed 80".
  - Alternative template: optional, one per channel (SMS text, or email subject
    and body). It's validated like the main content: allowed variables only, and
    its fixed text must be within the limit. The screen also shows how many
    recipients would still exceed it.
  - At send time: render the main template, use the alternative if it's over the
    limit, and skip with character_limit_exceeded if that's still over. Each
    message records which version it used, so the dashboard shows sent with main
    / sent with alternative / skipped.
  - Schema: fits as planned. campaign_content gets a variant (main/alternative)
    and messages records the variant used.
  - Exact counts: I'd compute them in the database with the same
    replace-and-tidy rendering as the Go code, so they're exact rather than
    estimates. A test would check that the two agree for all 3,000 seeded users.
  - Effect on decisions: this reverses D3's rejection of a fallback message, and
    it mostly makes the deferred "resend to skipped recipients" unnecessary.
  - Optional add-on: a "suggest shorter version" button that reuses the
    content-generation endpoint. I'd start with a manually written alternative.

  Combined risk: the counts the marketer sees, both audience and over-limit, are
  estimates of a future send. The UI has to say so clearly, and the dashboard
  has to show the real numbers.

     Scheduled sending flow (approved 2026-10-21; audience recalculated when 
     sending starts, replacing D8)

     0. Suggestion from the brief: the request is sent together with the
        browser's IANA time zone. Claude gets the current time and that zone,
        and returns suggested_send_at (RFC 3339 with offset) or null, plus
        schedule_note (the phrase it read, e.g. "yarın saat 10:00"). Vague
        timing ("sometime next week") → null with a note. The backend validates
        it: a bad format is invalid output and triggers the D15 retry. A
        parseable time outside the window (in the past, or more than 30 days
        ahead) isn't prefilled; the note explains why ("'yesterday 10:00' is in
        the past") and the rules are still used. A valid suggestion is stored as
        the draft's proposed send_at. It's advisory only; nothing is scheduled
        yet.
     1. Review and confirm: the review screen shows "Suggested from your brief:
        Tue 22 Oct, 10:00 (Europe/Istanbul)", with Schedule preselected and the
        time editable, or Send now. Approve always sends an explicit send_at (or
        now) from what's on screen, so a suggestion is never accepted
        implicitly. A draft changed since it was viewed fails the version check
        (D10).
     2. Approve: the marketer chooses Send now or Schedule (date and time in
        browser local time with the zone shown, stored in UTC). In one
        transaction (T9): check version, status draft, valid content, audience >
        0, and send_at: now → now(); scheduled → at least now + 1 min and at
        most now + 30 days; an absolute rule window starting after send_at → 422
        (it would match nobody). Rules and content are frozen and the current
        per-channel counts are stored as approval_estimate. No messages are 
        created yet. The screen shows: "412 recipients now (SMS 380 · 
        Email 301). The audience is recalculated when sending starts; the final 
        number may differ." The per-channel over-limit warning (D3) is shown the
        same way, as an estimate. The campaign gets status = approved and
        send_at.
     3. Waiting: no new status and no scheduler process. The UI shows "Scheduled
        for <time>". Rules, content and time can't be changed. Cancel sets
        approved → cancelled; there are no messages to touch yet. Rescheduling
        isn't supported: cancel and create a new campaign.
     4. Sending starts: the worker's BuildAudience step finds approved campaigns
        with send_at <= now() (FOR UPDATE SKIP LOCKED). In one transaction it
        evaluates the rules (relative windows counted from now), inserts
        messages per channel with consent (ON CONFLICT DO NOTHING), and sets
        audience_built_at and status = sending. "Send now" takes the same path
        within about 1 s. If the audience is now empty → completed with 0
        messages, shown on the dashboard. From then on the normal path runs:
        consent and cancel re-check, rendering, length check
        (skipped/character_limit_exceeded), rate limiter and retries (D7, D19).
        It ends as completed when every message is final. The dashboard shows
        "Estimated 412 at approval → 398 at send".
     5. Late start: if the worker is down at send_at, sending starts when it
        comes back, and relative windows are counted from that moment. The
        dashboard shows the scheduled time and the actual start
        (audience_built_at).
     - Known trade-off: the approved count is an estimate. Once a send has
       started, users who stop matching aren't removed; only consent is
       re-checked.

     Resend to skipped recipients (approved 2026-10-21; no alternative templates
     at approval)

     - The dashboard shows skipped counts per reason and channel. For
       character_limit_exceeded it offers "Resend to 37 skipped (SMS)", enabled
       once the original campaign is completed or cancelled.
     - This creates a draft follow-up campaign with parent_campaign_id, a single
       channel and no rules. Its audience is the fixed list of the parent's
       messages on that channel with skip_reason = 'character_limit_exceeded',
       minus any user with a sent message on that channel in the parent. It is
       never recalculated from rules.
     - The marketer writes (or generates, T8) a shorter template, sees the
       over-limit count for that list, and approves now or scheduled. Sending
       uses the same path: consent re-checked, rendered, length-checked, skipped
       again if still too long. It can itself be resent.
     - At most one non-cancelled resend per (parent, channel) at a time (partial
       unique index), so two marketers can't resend twice.

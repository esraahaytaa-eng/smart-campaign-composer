# T20 — Product bonuses

**Status:** proposed 2026-10-24, waiting for approval. Nothing is built until decisions A–H are approved and recorded (D64, D65).

**Sources:** `CASE.md` §9 (optional features: A/B testing, messages in the user's language); `DECISIONS.md` D3, D14, D15, D31, D32, D50 (T20 scope), D63; the code on `main` at `256252f`.

**Branch:** `feature/t20-product-bonuses` from `main`, one draft PR, merged only with your approval. T19 Step 8 (exploratory QA) stays postponed until all feature work is done.

**Method:**
- TDD for every change (Red → Green → Refactor), small commits.
- Focused tests while working; `make test`, `make lint`, `make scan` and `make e2e` at the end of each task that changes behaviour.
- Every commit and push is scanned first (D50, D51).
- Each task ends with a short report; anything that needs a decision comes to you first.

**Goal:** each recipient gets the campaign in their own language (Turkish, English or German), falling back to English. A/B testing is evaluated and, as recommended here, not built.

**Architecture:** content becomes a set of language variants (`en` always present, `tr` and `de` optional) that share the campaign's channels. The worker sends each recipient the variant for their language, else English. The choice is fixed when the audience is built. One AI call writes all requested variants, so the D63 limit counts it once.

**Tech stack:** unchanged (Go, Postgres, Vue 3, the existing Claude client and mock). No new dependencies.

## Decisions needing your approval

| | Proposal (recommended) | Alternative and why not | Record |
|---|---|---|---|
| A | **English is always required.** It is the fallback, so every recipient always has a message, including people who join the audience after approval. | *English only when some audience language has no variant:* less to write, but the audience is rebuilt at send time, so a missing fallback could leave recipients with no message. | D64 |
| B | **Variants default to the languages in the audience, plus English.** The marketer can add or remove Turkish and German, but not English. | *All three always:* the marketer has to write and review German for an audience with no German speakers. | D64 |
| C | **One AI call writes every requested variant.** The same endpoint can write a single added language (e.g. German only) without touching the others. | *One call per language:* each send costs up to 3 of the 10 hourly AI calls (D63), and the variants can drift apart. | D64 |
| D | **German speakers in the demo data: 5% of users** (`id % 20 = 0`, 150 of 3,000). Fresh databases get them from the seed generator; existing ones from a migration using the same rule. No other seeded value changes. | *Fresh databases only:* your local data would have no German speakers without `down -v`, which deletes your campaigns. | D64 |
| E | **The language is fixed when the audience is built** (`messages.language`). Retries and the results screen use that choice. | *Chosen on each attempt:* a retry could switch language mid-send, and the results couldn't say what was sent. | D64 |
| F | **Content written before T20 becomes the English variant.** It is still sent to everyone, exactly as before, even if it is in Turkish. | *Guess its language:* unreliable, and could change what an already-approved campaign sends. | D64 |
| G | **A/B testing is not built.** The system records delivery but no outcome (no opens, clicks or orders after a send), so a winner can't be measured. Building it would double the content model on top of languages for a number nobody can read. The evaluation is recorded instead. | *Build A/B with a delivery-only report:* it looks finished but answers nothing. | D65 (Deferred) |
| H | **D32 is narrowed:** the brief can be in any language; each variant is written in its own language. Unsupported-brief reasons stay in the brief's language. | — | D32 history |

## Global constraints

- The AI never receives customer data (D15): it gets the brief, the channels and the language codes, never users or counts per user.
- Only `{{first_name}}`, `{{last_name}}` and `{{city}}`; SMS ≤ 160, subject ≤ 80 and email body ≤ 2,000 characters after personalization, in every variant (D3).
- AI output is untrusted: every variant goes through `ValidateDraft`, and a wrong or missing language is a validation error, retried once like today and never filled in silently.
- Languages are exactly `tr`, `en`, `de`. Anything else is refused with `422`.
- UI text in English and Turkish only (D58). German appears only in message content.

## Review focus

The likely failures no task's main path covers, each pinned by a test in the task named:
1. **A pre-T20 approved campaign** sends exactly what it sent before (Task 2 migration test, Task 4 worker test).
2. **A language is removed after generation:** its speakers move to English, and the estimate and preview follow (Tasks 3 and 6).
3. **A channel is removed after generation:** it disappears from every variant, not only English (Task 2).
4. **The AI returns a missing, extra or mislabelled language:** validation error, one retry, then the same error UI as today (Task 5).
5. **A recipient's language changes after the audience is built:** they still get the language that was recorded (Task 4).

### Task 2 — Content variants: storage, validation, API (A, F)

- **API:** `PUT /api/campaigns/{id}/content` takes `{version, content: {"en": {sms, email}, "tr": {...}}}`; `GET` returns the same shape. `saveContent` / `loadContent` work on `Variants`. Removing a channel (http.go:264) already deletes it for every language; a test pins that.

### Task 3 — Audience by language; per-language estimate (B)

**Files:** modify `internal/campaign/approve.go`, `internal/content/estimate.go`; tests next to each.
- **Counts:** `countAudience` also returns `Languages map[Lang]int` (recipients per language for the chosen channels). It is used by the estimate endpoint, the content screen (default variants, B) and approval.

- **Tests:**

### Task 4 — Send in the recipient's language (E)

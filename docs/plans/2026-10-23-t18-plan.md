**Status:** approved 2026-10-23 and implemented the same day (steps 1–8). Decisions D45–D49. Performance results in `docs/performance.md`.

**Sources:** `CASE.md` §3 Monitoring; D16, D30, D31, D36, D44, D45; the design boards B (dashboard), C (campaigns), 4 (live delivery), 5 (recipient details), 6 (resend); the main plan's T18 entry.

**Method:** inline execution, TDD for every step (failing test → pass → refactor), one commit per step, approval before T19. `make test`, `make lint` and `make e2e` before the task is reported done.

## What exists today

- `GET /api/campaigns` (newest 200, every field, no message counts), `GET /api/campaigns/{id}`, `POST …/cancel`, `POST …/resend {channel}` (creates a draft follow-up, D31).
- `GET /api/campaigns/{id}/events`: per-channel snapshot (audience, counts by message status, retries, 429 totals, skip reasons, top raw `last_error` strings, an `uncertain` flag count, resendable count, active resend id), `end` when finished (D36).
- `messages` (status, `skip_reason`, `last_error`, `attempt_count`, `next_attempt_at`, `delivery_uncertain`) and `delivery_attempts` (attempt no, start/finish, outcome, HTTP status, error).
- Frontend: Dashboard and Campaigns are placeholders; a non-draft campaign page shows only "can no longer be edited".

## Decisions this plan needs (A–G)

Each is my proposal with the reason; approving the plan approves them, and they go into DECISIONS.md as D46+ (D45 already records that recipient details are in scope).

**A. One display vocabulary for delivery outcomes.** The design treats *Uncertain* as its own group; in the backend it is a flag (D5) that can sit on any status. Proposed groups, computed by one SQL expression shared by the status stream and the recipient API:

| Group | Messages |
|---|---|
| Sent | `sent` (an earlier timeout no longer matters: the provider accepted it, same key) |
| Uncertain | `failed`, `skipped` or `cancelled` **and** `delivery_uncertain` |
| Failed | `failed`, not uncertain |
| Skipped | `skipped`, not uncertain |
| Cancelled | `cancelled`, not uncertain |
| Retrying | `retry_scheduled` |
| Pending | `pending` and `sending` ("queued or being sent now") |

So the groups add up to the audience, and "Uncertain" means exactly what the design says: attempted, may have been accepted, never resent (matches D31's exclusion).

**B. Reasons as codes, not provider text.** The API returns reason codes the UI translates (D44), never raw `last_error` or provider error text (privacy and translation):
- failed: `provider_rejected` (last attempt `rejected`, e.g. HTTP 400), `retries_exhausted`
- skipped: `character_limit_exceeded` (with the rendered length and limit, e.g. 165 / 160, computed on the server from the approved content), `no_consent`
- uncertain: `timeout`, `network_error`, `interrupted`, `no_response_recorded` (worker died mid-attempt)
- retrying: last attempt's outcome (`rate_limited`, `server_error`, `timeout`, `network_error`, `interrupted`) and the next attempt time

**C. Status stream changes (T14 API).** Add `groups` (A) and `reasons` (B) per channel, and `rate_limited_recent` (429s in the last 5 minutes, the design's wording) next to the existing total. Remove the raw `failure_reasons` and redefine `uncertain` as the group count. Nothing in the frontend reads these fields yet; the Go tests that do are updated.

**D. Recipient API with privacy protection.**
`GET /api/campaigns/{id}/recipients?group=failed&channel=sms&q=ayş&page=1`
- `group` required (one of A), `channel` optional (`sms`/`email`), `q` optional (name search), `page` ≥ 1. 50 rows per page, fixed.
- Sorted by last attempt (newest first, never-attempted last), then message id, as in the design.
- Response: `as_of`, counts per group and channel (for the tabs), reason counts for the chosen group and channel, `total` for the filter, and the page of rows: message id, name, masked contact, channel, group, reason code and detail, attempt count, last attempt time, next attempt time, and the attempt history (number, start time, outcome, HTTP status; at most 5 + interrupted ones per message, so it is inline instead of a second endpoint).
- Unknown campaign → 404; bad parameters → 422; campaigns without messages (draft, scheduled, cancelled before sending) → zero counts and no rows.
- Privacy:
  - Contacts are masked in SQL/Go before they leave the server: phone `+90 555 ••• •• 17` (country and operator prefix, last two digits); email first 3 characters of the local part + `•••@domain`. The full phone or email is never in a response.
  - Search matches names only (first + last, Turkish-folded, case-insensitive, substring; `q` ≤ 50 characters, LIKE wildcards escaped, parameterized). There is no search by phone or email, so the API can't be used to check whether a given contact is a customer.
  - No raw provider or error text (B), no message body, no other user fields (city, consent, orders).
  - Fixed page size, no export.
  - `Cache-Control: no-store`. The query string is not logged (the metrics label is the route pattern, already true). Sign-in required like every API route; all marketers share one role (D10).
- Paging is offset-based. A campaign has at most 2 × 3,000 messages here, so this is cheap. While sending, rows can move between pages; the drawer is a snapshot (`as_of` shown, as in the design: "reopen to refresh"). `shortcut:` comment noting keyset paging if audiences grow.

**E. Resend uses the T17 screens.** The design's resend page (board 6) edits a shorter SMS and approves in one dialog. In the backend a resend is a draft with its own content and approval (D31). Proposed: "Resend shorter SMS →" opens a dialog with the design's "Who gets the resend" / "Not included" numbers (skipped for length, estimated eligible, consent revoked, uncertain, failed), then creates the follow-up and opens its content step (T17), where the original SMS is shown in a "Show original SMS" disclosure. Approval is the T17 review step. Any channel with length skips gets the offer (the backend allows email too).

**F. Campaign list: search and filters in the browser.** The list endpoint already returns the newest 200 campaigns; status filters, counts and "Search by brief" (Turkish-folded) run on that list in the browser. No backend change. Limit noted in the README (`shortcut:` comment: server-side filtering when there are more than 200 campaigns).

**G. The dashboard shows only what is cheap and exact.** Status cards (Drafts, Scheduled, Sending, Completed, Cancelled) and "Your campaigns" (sending first, then drafts, scheduled, then the rest by date; 6 rows; "View all"). The design's "N SMS can be resent" hint on dashboard rows needs a per-campaign count the list doesn't have, so the dashboard says "Finished · results are ready" and the resend offer lives on the campaign's page.

## Steps

### Step 1 — Delivery groups and reasons in the status stream (backend)
- One SQL expression for groups (A) and one for reason codes (B), in `internal/campaign`.
- Snapshot gets `groups`, `reasons`, `rate_limited_recent`; `failure_reasons` removed; `uncertain` redefined.
- Tests (fixture messages and attempts): every row of table A including uncertain on failed/skipped/cancelled and an uncertain flag on a sent message; groups sum to the audience; each reason code; 429s older than 5 minutes are only in the total.
- **Done when:** the snapshot tests and the existing `internal/e2e` tests pass.

### Step 2 — Recipient API (backend)
- `GET /api/campaigns/{id}/recipients` as in D.
- Tests: filters by group/channel/name (Turkish: `ayşe` finds `Ayşe`, `ISIL` finds `Işıl`, `%` and `_` are literal); paging and total; sort order; reason codes and the 165/160 detail; attempt history order; masking (the full phone and email never appear in the response body for any row, checked over a whole page); 404, 422 for each bad parameter, `q` over 50 characters; empty campaign; signed-out → 401; `Cache-Control: no-store`.
- **Done when:** these tests and the full Go suite pass.

### Step 3 — View models (frontend, pure TypeScript)
- `delivery.ts`: from a snapshot → summary cards (total, sent %, not sent, uncertain, in progress), per-channel rows and bar segments, processed %, estimate vs actual with the difference, "scheduled" vs "sending started at" vs "cancelled before sending", and when resend is offered (finished, resendable > 0, no active resend; "available when sending finishes" while sending).
- `campaignList.ts`: status counts, filter, brief search (Turkish fold), dashboard ordering and row hint, actions per status (Delete/Edit, Cancel/View, Cancel/Monitor, View results), resend link to the parent.
- `recipients.ts`: query ↔ URL state, reason and attempt labels by code.
- Vitest for each: the main plan's "status aggregation including the scheduled state and when resend is offered", plus empty and zero cases.
- **Done when:** Vitest and the type check pass.

### Step 4 — Dashboard and Campaigns pages
- Boards B and C from the view models: status cards, "Your campaigns", the full list with filters and search, actions; delete (drafts) and cancel (approved/sending) each confirm first (existing `ConfirmDialog`).
- **Done when:** every row's action leads to the right screen, and the pages work in TR and EN.

### Step 5 — Campaign page after approval: scheduled and live delivery
- Approved: "Sending starts …" (local time), estimate per channel, locked content, cancel with confirmation (design's text: it won't send, can't be undone).
- Sending/completed/cancelled: board 4. Audience estimate vs actual, summary cards, per-channel bars and group rows (each opens recipient details with that group and channel), retries and 429s ("in the last 5 min" and total), "Counts as of …", Live / Pause, cancel while sending.
- `EventSource` on `/events`: closed on `end` (D36), on Pause and when leaving the page; the browser's own reconnect handles drops; the campaign is fetched again after `end` and after a resend.
- A resend's page links to its parent; the parent links to its resend.
- **Done when:** a send from the composer shows live progress until completed, and a scheduled one shows its time and can be cancelled.

### Step 6 — Recipient details drawer
- Board 5 as a side dialog (Reka UI, focus trapped, Escape closes and returns focus to the row that opened it), state in the URL query so Back closes it and a link reopens it.
- Group tabs with counts, channel switch, name search (on submit or after a pause), reason box, table with expandable attempt history, "Showing 50 of N · sorted by last attempt", previous/next page, empty states, and the resend link on Skipped.
- **Done when:** filters, paging and history work against the API in TR and EN, and keyboard-only use works.

### Step 7 — Resend flow
- Dialog from E, `POST …/resend`, then the follow-up's content step with "Show original SMS". A 409 (already resent, nothing to resend, still sending) shows the server's reason (D44 errors) and reloads the status.
- **Done when:** a too-long SMS send → resend → only the skipped recipients get the shorter message (checked with the existing mock providers).

### Step 8 — Languages, browser tests, docs
- All new text in `en.ts` and `tr.ts`; the coverage scan passes.
- Final QA (requested 2026-10-23): watch a campaign mid-send (counts moving, Live · pause and resume) and cancel it while sending (only unsent messages become cancelled, the stream ends), in the browser and as `make e2e` checks.
- `make e2e` additions: live delivery reaches completed; recipient drawer filters, search, paging and masked contacts; cancel a scheduled campaign; resend flow; Turkish screens.
- README: dashboard, live delivery, recipient details and privacy, resend; move the "Differences to settle" items to "Changes from the design"; limits (200-campaign list, offset paging, snapshot drawer). DECISIONS.md: A–G as D46+, close the open question.
- **Done when:** `make test`, `make lint` and `make e2e` pass and the main plan's verification walk-through works in the browser.

## Out of scope

- The small T17 leftovers (screen-reader announcement details, the "changed elsewhere" wording after Stop, logout within 1.5 s of typing). They stay listed and can be a separate fix.
- Archiving, an aggregate "all campaigns" delivery chart, exports, recipient search by phone or email.

## Risks

| Risk | Mitigation |
|---|---|
| Customer data in a new API | Masking in one place, no contact search, no raw errors, tests that scan whole responses |
| Group mapping disagrees between stream and drawer | One shared SQL expression, tested once |
| Many open streams (README limitation) | Close on `end`, Pause and leaving; unchanged otherwise |
| Rows shift between pages while sending | Snapshot drawer with "as of" time; noted in README |
| T18 is the largest frontend task | 8 steps, each committed and testable on its own |

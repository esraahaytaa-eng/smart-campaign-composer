## Steps

### Step 1 — Secret and personal-data scanning (A)
- `make scan` with gitleaks plus repository rules for emails and phone numbers. Allowed: the seed's fictional data, `@example.com`, the documented demo login and test fixtures.
- **Verification:** a test commit with a fake key (`sk-ant-…`), a real-looking email and a `.env` file is caught. The current tree is clean, apart from known allowed items listed in the config.
- **Exports:** the scan also covers `ai-sessions/`. `05`, `06` and `07` are redacted (names, usernames and emails replaced by roles) before they're committed; `04` is left as is (your choice).
- **Done when:** `make scan` fails on each planted secret and passes on the real tree.

### Step 2 — Faster and steadier tests
- **Go:** run migrations once into a template database and create each test database from it, plus a seeded template for the tests that need 3,000 customers. The test Postgres gets throwaway settings (`fsync`, `synchronous_commit` and `full_page_writes` off; it's already on tmpfs).
- **`make test`:** Go and the frontend run at the same time; package installs are skipped when the lockfile hasn't changed (frontend and browser suite).
- **Browser suite (C):**
  - the separate stack;
  - campaigns that several files need are sent once per run and shared;
  - independent files run in parallel, apart from the dashboard-count file.
- **Flakes:** every test that waits a fixed time is reviewed and made to wait on a condition (the pattern of the two fixes before the merge).
- **Done when:** the test targets T1–T3 below are met, and 5 consecutive full runs pass with no failures.

### Step 3 — CI (B)
- `.github/workflows/ci.yml` runs `make test`, `make lint` and `make scan` on every push and PR.
- `e2e.yml` runs the browser suite manually and nightly, and keeps screenshots of failures as artifacts.
- The README gets a CI badge and a section on what runs where.
- **Done when:** a PR shows the checks passing, and a planted failing test and a planted secret each make CI fail. Both plants are removed afterwards.

### Step 4 — Security: customer data, authorization, API security (E, F)
Reviewed against a checklist with `file:line` evidence for each item. Each finding is fixed with a failing test first, and anything beyond E and F is brought to you before fixing.
- **Customer data:**
  - recipient contacts masked everywhere they leave the server (recipient API, status stream, errors);
  - no customer fields sent to the AI (D15), checked in the prompt builder with a test;
  - nothing personal in logs (a test that captures log output during a send and a failed request);
  - the provider's database role limited to its own table (D6);
  - customer data never cached (F).
- **Authorization:**
  - every `/api` route requires a session (a test that walks every registered route);
  - every campaign route returns 404 for unknown ids, with no other campaign's data in errors;
  - health and metrics stay open (D10) but expose no customer data.
- **API security:**
  - CSRF: the cookie is SameSite=Lax, and every state-changing route requires a JSON body; a test sends form-encoded and missing content types;
  - body and field size limits on every endpoint;
  - SQL only through parameters (rule builder and search);
  - error responses never echo internals;
  - session expiry and logout;
  - login throttling (E).
- **Dependencies:** `govulncheck` and `npm audit` (app and browser suite).
- **Done when:** every checklist item has a result and evidence; approved fixes are tested.

### Step 5 — Server-side campaign list (D)
- The API from D, with tests for:
  - each filter, search (Turkish letters, `%` and `_`), paging past the end, invalid input (422), totals and counts;

- The list and dashboard use it, and filters stay in the address.
- The 200-campaign limit and its README note are removed.
- **Done when:** the list and dashboard are correct with more than 200 campaigns (a test inserts 250), and performance target P4 is met.

### Step 6 — UX and responsive work
- **Sidebar:** scrolls on short screens, keeps the account menu reachable, and the Turkish mode badge no longer wraps.
- **Log out:** reachable and announced by keyboard and screen reader; focus lands on the sign-in page's first field.
- **Layouts at 1440, 1024, 768 and 375 px:**
  - dashboard cards;
  - campaign table (stacked rows on narrow screens);
  - composer columns;
  - delivery cards and channel sections;
  - recipient panel full screen on phones;
  - dialogs.
- Small UX items from the QA notes so far.
- The translations chunk (H).
- **Done when:** the browser suite has screenshot checks at the four widths with no horizontal scrolling, and the keyboard-only checks for the shell and sign-out pass.

### Step 7 — Performance testing (G)
- **Baseline first:** each target below is measured before any change, on a quiet machine, recorded in `docs/performance.md`.
- **Tools:** Go tests behind a `perf` build tag (`make perf`; standard library only, no new tools):
  - a full send;
  - concurrent marketers on the API;
  - concurrent live screens.
- Bundle size from the build.
- **Fixes:** anything that misses a target is measured before and after the fix; otherwise it's documented with its upgrade path.
- **Done when:** every target is met, or its gap is explained and agreed with you.

### Step 8 — Independent exploratory QA and fixes
- **The tester:** an independent agent without my notes, given `CASE.md`, the README and the running app. It explores freely in English and Turkish: odd inputs, very long and empty texts, quick double actions, two tabs, expired sessions, slow and failing network, many campaigns.
- **Seeded starting points:** two low items from the PR #6 review, the retry count after a hand-back and the connection-drop race.
- **Its output:** a ranked list of findings.
- **My part:** I verify each finding and bring you the list with recommendations. Approved fixes get tests.
- **Done when:** every finding is fixed, documented or rejected with your agreement.

## Performance targets (G)

Measured on this machine (Docker Desktop, 8 CPUs, 8 GB), warm, with the 3,000-customer seed, mock AI and mock providers at their default failure rates. "p95" is the 95th percentile over at least 200 requests.

| # | Target | Measured how |
|---|---|---|
| P1 | **A send to every consenting customer on both channels** (4,191 messages, about 2,100 per channel): 95% final within **35 s**, all final within **75 s** of sending starting. The theoretical minimum is about 21 s at 100/s per channel; the rest is retries (1, 2, 4, 8 s) and 5 s timeouts. | Start and finish times from the database |
| P2 | **Rate limit never exceeded:** at most **100** provider requests in any 1-second window per channel during P1, retries included. A hard requirement, not a target. | Sliding window over recorded attempt times |
| P3 | **10 concurrent marketers** for 2 minutes (list, campaign, estimate, recipients, edits): p95 **≤ 200 ms** for reads and **≤ 300 ms** for writes (mock AI excluded), **0** server errors. | `make perf` load test |
| P4 | **Campaign list** (step 5) with 10,000 campaigns: p95 **≤ 100 ms** for a page with search and filter. | Same load test, larger fixture |
| P5 | **Recipient details** on 6,000 messages: p95 **≤ 50 ms** (the single-request benchmark is about 20 ms today). | Same load test |
| P6 | **20 live screens** on one sending campaign: total database time **≤ 400 ms per second**, and each screen's update **≤ 2 s** behind the database. | Database statistics during P1 |
| P7 | **Frontend first load:** JavaScript for sign-in and the dashboard **≤ 100 kB gzipped**; largest single chunk **≤ 40 kB gzipped** (51 kB today). | Build output |
| T1 | **`make test` wall time ≤ 50%** of the baseline measured at the start of step 2. | Timed runs, same machine, quiet |
| T2 | **`make e2e` wall time ≤ 50%** of its baseline. | Same |
| T3 | **No flaky failures:** 5 consecutive full runs of every suite pass. | Repeated runs |

## Risks

| Risk | Mitigation |
|---|---|
| Template databases change how every test starts | One shared helper, a test that each test database is empty and independent; the whole suite run several times |
| CI differs from this machine (Linux runner, no Docker Desktop) | Everything already runs in Docker; first CI runs watched; machine-specific parts documented |
| Too many scanner false positives slow commits down | Repository allow-list for the fictional seed and demo data, reviewed in step 1 |
| A strict CSP breaks something at runtime | The browser suite fails on CSP violations (console checks) |
| Performance targets missed on this laptop | Baseline first; gaps are reported with numbers before anything is changed |
| Server-side list changes break the dashboard | Browser checks for counts and filters with more than 200 campaigns |
